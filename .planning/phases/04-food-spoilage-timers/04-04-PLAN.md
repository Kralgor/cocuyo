<objective>
Implement local food spoilage warning notifications for tracked food timers.

This plan covers NOTF-03 with local Expo notifications scheduled before tracked
items reach their configured threshold. It preserves FOOD-03 and FOOD-04
semantics by scheduling only for active saved-zone timer sessions, using the
same outage start, canceling/resetting on restoration, and deduplicating alerts
locally.

Covers D-09 food warnings before unsafe threshold, D-10 simple local-first
notification behavior, D-11 point-of-use permission requests, D-15 notification
or prompt on outage detection, D-16 cancellation/reset on restoration, D-17
cautious early warnings, and D-18 stale/offline scheduling from last known
outage start.
</objective>

Existing constraints:
- Use `expo-notifications`, already present in the mobile package. Do not add a
  package install.
- Prefer local notifications. Do not register food timers, food names, or food
  state with Supabase.
- Request OS notification permission only when the user enables food alerts or
  confirms timer tracking during an outage. Never during onboarding or Food tab
  initial render.
- Keep notification preferences local in MMKV under `foodNotificationPrefs`.
- Keep dedupe state local in MMKV under `foodDismissedWarnings`.
- No backend schema, accounts, sync, pantry management, barcode scanning,
  sensors, or household sharing.
</context>

<decision_coverage>
- D-09: Schedule warnings before thresholds, not only at expiration.
- D-10: Use local-first Expo notifications; no account, identity, or push
  pipeline dependency for food state.
- D-11: Permission request is triggered only by explicit Food alert user action.
- D-15: Outage detection can produce a local review notification when appropriate

- D-17: Notification copy is cautious and early: "revisa", "evita abrir la
  nevera", and "si tienes dudas, descarta".

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Food timer state -> local notification scheduler | Local state controls when OS notifications fire. |
| User action -> OS permission request | Permission prompt must occur only after explicit action. |
| MMKV scheduled IDs -> cancellation | Stored IDs may be stale or corrupt. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-04-01 | Information disclosure | Food notifications | mitigate | Do not send food state to Supabase; local notification data contains only local item/session identifiers. |
| T-04-04-02 | Denial of service | Duplicate notifications | mitigate | Store scheduled IDs and dismissed warning keys; dedupe by session/item/warning level. |
| T-04-04-03 | Spoofing/consent | Permission request | mitigate | Request OS permission only from explicit Food alert enable/review action. |
| T-04-04-04 | Safety | Warning copy | mitigate | Warn early with cautious language and no guarantee that food is safe or unsafe solely from unknown temperature. |
</threat_model>
